### Spec 1: `ledger-core` (Oct 31, 2026)
- **Generated by Kiro:** `.kiro/specs/ledger-core/` with 9 requirement groups in EARS format, a design (Drizzle schema, pure functions vs repository, `LedgerError`, test strategy) and 32 tasks. The input was the "Spec 1" section of `docs/brief.md` plus the steering files.
- **Spec review (one revision round, done by Kiro on request):**
  - `computeBalance` clamped with `Math.max(0, …)`, which made "balance never negative" pass trivially. It now returns the exact difference, and over-payment rejection is what guarantees the invariant.
  - Foreign keys had been "omitted for brevity". They were added, along with `CHECK amount_tzs > 0`.
  - `recordPayment` now runs in a transaction with `SELECT … FOR UPDATE` on the customer row, so concurrent payments can't overdraw.
  - Added a P5 property test against the real repository, and switched to drizzle-kit generated migrations.
- **Implementation:** Kiro wrote all the code in `server/` in three passes: scaffold + pure layer (T1–T9), schema + repository (T10–T19), tests (T20–T31). Between passes we ran `npm install`, `drizzle-kit generate`, `tsc` and `vitest`, and pasted the failures back to Kiro.
- **What had to be corrected (every fix was made by Kiro from feedback):**
  - `maskPhone` sliced one character too many.
  - `normalisePhone` threw a plain object containing the full phone number. It now throws a `LedgerError` class with a masked number.
  - `defaultDueDate` used local `setDate` and now adds exactly 7×24h.
  - 20 `possibly undefined` errors under `noUncheckedIndexedAccess`.
  - P5 timed out because it created a PGlite database per run. It now uses one database and isolates each run with fresh rows.
- **Spec vs vibe:** the spec round caught the clamping and concurrency bugs before any code existed. Those are exactly the subtle money bugs that vibe coding tends to ship. The remaining bugs were small and mechanical, and the test loop caught them. Model note: `auto` was throttled by the service at the time, so the implementation ran on `claude-sonnet-4.5` through `kiro-cli chat --no-interactive`.

## Property-based testing
_(fast-check: ledger invariants, USSD state machine never exceeds 182 characters)_

### ledger-core (fast-check 3 + Vitest; 59 tests green, of which 5 are properties)
- **P1:** after any random sequence of debts and validated payments, the raw balance is never negative.
- **P2:** shuffling the order of payments never changes the final balance.
- **P3:** `totalOwed` equals the sum of each customer's balance (up to 20 customers).
- **P4:** any payment greater than the outstanding balance is rejected.
- **P5:** a random command sequence against the real Drizzle repository on in-process PGlite (25 runs) matches the pure model and never goes negative. No external Postgres is needed.
